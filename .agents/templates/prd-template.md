# PRD Template

This is a template guiding generation of specifications for a project or a feature.

## Overview

Defines the project or feature at a high level.

- ✅ Name, short description, scope.
- 🚫 No technical details or implementation steps.

## Problem statement / Why

States the reason for the project or feature.

- ✅ Problem definition, context, constraints.
- 🚫 No solutions or design details.

## Goals and Non‑Goals

Clarifies scope boundaries.

- ✅ Explicit goals, explicit non‑goals, measurable outcomes.
- 🚫 No vague aspirations or unrelated ideas.

## Requirements / What

Specifies functional and non‑functional requirements.

- ✅ Feature list, workflows, acceptance criteria, performance/security requirements.
- ✅ Structured interaction statements in the form of *actor* → *action* → *result*.
- 🚫 No architecture diagrams, code snippets, or implementation notes.

## User Stories

Illustrates how different users will interact with the feature.

- ✅ Structured as "As a [persona], I want to [action], so that [benefit]."
- ✅ Concrete scenarios with clear user value.
- 🚫 No implementation details or technical architecture.

## Design & Architecture / How

Outlines the intended solution approach.

- ✅ Architecture diagrams, data models, API contracts, UX flows (if relevant).
- 🚫 No timelines, personal notes, or rationale repetition.

## Public API

Defines the external interfaces exposed by the project or feature.

- ✅ API endpoints, function signatures, input/output contracts, error responses.
- ✅ Authentication/authorization requirements, rate limits, versioning strategy.
- 🚫 No internal implementation details or private functions.

## Project Structure

Describes the organization of the codebase and key components.

- ✅ Directory layout, module organization, key files and their purposes.
- ✅ Dependency relationships between components, configuration files.
- 🚫 No implementation code or detailed function-level descriptions.

## Implementation plan

Captures the plan for building.

- ✅ Sequence of steps, external dependencies, risks.
- 🚫 No test cases or high‑level goals.

## Validation & Testing

Defines how correctness will be verified.

- ✅ Acceptance criteria, test strategy, metrics, reproducibility checks.
- 🚫 No requirements (already in Requirements) or implementation notes.

## Appendices (if applicable)

Holds supporting material.

- ✅ Glossary, references, research links.
- 🚫 No critical requirements or goals.
